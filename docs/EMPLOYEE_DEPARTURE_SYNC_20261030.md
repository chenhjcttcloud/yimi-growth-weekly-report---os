# 员工离职状态同步

## 生效方式

在「系统设置 → 员工管理」点击「同步公司全部人员」，或在组织部门页面同步飞书部门时，会核查员工状态。飞书 SSO 登录时也会检查其返回的明确账号状态。本次没有新增通讯录定时轮询；不能把部署或页面刷新理解为已经同步了飞书。

员工页默认显示「在职」。已停用人员保留在「已停用」和「全部」中，可以手动恢复。恢复沿用现有在职区间规则，从恢复当天生效，不回填停用期间的缺交，也不自动重开旧评分关系。

## 判断规则

- 以飞书 `user_id` 为唯一身份依据。
- 当前目录返回明确的 `status.is_resigned`、`status.is_frozen` 或 `status.is_unjoined` 布尔值 `true` 时自动停用。
- 原有人员从部门名单中消失时，另外查询其精确 `user_id` 资料；仅匹配同一身份且明确返回上述状态时停用。
- 未返回状态、状态为字符串、身份不匹配、权限错误、网络错误或 404 都不作为离职证据。原有在职账号保持原状，并计入「状态待核查」。
- 查询缺失人员不会将其重新计入本次发现的公司人数，不改变公司覆盖范围统计。
- 手动停用不被通讯录或 SSO 自动恢复。停用日期处理失败会在后续明确状态核查时重试。

如果飞书只返回基本资料而没有账号状态，需要先核实接口返回字段和授权；本功能不会猜测该账号已经离职，也不会据此自动停用真实员工。

## 停用后的行为

- 现有登录会话访问 API 时立即被拒绝；新登录也不获得有效员工访问权限。
- 不再出现在在职人员、新评分配置或提醒收件人名单中。
- 同事互评、负责人评分停止展示其未完成任务；旧页面直接提交也被服务端拦截。
- 评分写入时再次检查员工及评分人的状态，避免读取页面后发生停用仍写入分数。
- 已提交的评分保留只读；历史周报、成绩、在职区间和已冻结评分范围保留。
- 不因评分人被停用而缩减原有评分分母或自动发布不完整结果；需要交接的负责人任务继续按既有交接流程处理。
- 不物理删除账号、评分关系、业务数据、文件或备份。

## 验证

`npm run test:business` 包含 50 组业务测试及 TypeScript、构建，共 52 项检查。离职专项包括：

- `test-company-directory.mjs`：精确状态、资料缺失、权限与网络失败、重复资料、空公司名单、停用区间重试。
- `test-sso-roster.mjs`：首次与已有账号的明确停用状态、身份匹配、状态缺失及手动停用保护。
- `test-employee-departure-api.mjs`：同步后已有会话失效、旧评分入口被拦截、正常在职评分仍可提交、提醒过滤、历史和冻结范围不变。
- `test-employee-departure-manager.mjs`：负责人和老板评分、读取与写入之间的并发停用、历史保留、恢复与交接。
- `test-company-roster-ui.mjs`、`test-manager-reviews-ui.mjs`：默认在职筛选、停用名单与恢复、状态待核查说明、错误提示、桌面和移动端内部滚动。

测试仅使用隔离数据，拦截外部请求，不发送真实飞书消息。测试数据库、日志和截图保留在 `outputs/tests`。本次本地验证不构成生产部署或仓库推送授权。
