# 周报质量成长教练离线试评留档

2026-11-19 更新：四类岗位的真实周报校准完成，用户已确认采用新规则，并明确授权本次生产部署和双仓库推送。本文件保留离线试评流程说明；正式接入及发布标识见 `WEEKLY_QUALITY_COACHING_20261119.md`。

下述离线工具只提供本地试评和四份实际周报的新旧对比，不接入自动同步、不写回历史分数、月度结果或趋势。人工校准确认与正式代码接入已完成；离线试评数据仍不作为正式评分写回。

## 评价范围

本评分仅用于评价周报的信息完整度、沟通价值与复盘质量，不代表对员工绩效或工作价值的最终评价。

清楚交代“对象＋事项＋当前状态”就是有效信息。认可建联、需求确认、报价、送样、测试、谈判、订单确认、交付、回款等阶段推进，不以最终成交作为唯一成果。不以篇幅、数字或附件多少决定分数，也不因暴露尚未解决的问题而重罚。

证明材料只用于管理抽查，不深挖、不强制提供、不作为正常评分门槛。合同、截图、付款凭证、文件编号等不进入公开周报。候选没有证据等级、附件折扣或分数上限；评分理由引用本份周报原文，仅用于追溯模型判断，并不要求员工额外交材料。只有原文明确异常、矛盾或管理者主动请求时，才可出现“如有需要可进一步核实”，是否抽查由管理者决定。

每模块展示评分理由、做得好的地方和最多两条建设性建议。“可以补充”用于建议，不逐项重复挑错。候选对照页不展示证据等级，不公开原文，不提供发布或写回按钮。

## 分值

| 模块 | 细项 | 分值 |
|---|---|---:|
| 本周成果 | 有价值的实际工作或业务推进／完成结果或阶段进展／对象与状态清楚／客户、团队或业务价值 | 12＋10＋5＋3＝30 |
| 问题与挑战 | 问题具体／原因或背景／影响或风险／已采取动作、下一步或所需支持 | 10＋6＋5＋4＝25 |
| 思考与复盘 | 具体事件／原因、得失或判断／下次改进动作／可复用经验 | 6＋6＋6＋2＝20 |
| 下周计划 | 可执行动作／岗位与当前工作相关／重点优先级／必要阶段节点／关键依赖或风险 | 10＋6＋4＋3＋2＝25 |

作者默认是责任人，下周计划默认期限为下周。只有必要的跨部门协作或特殊节点才需要额外说明负责人、资源和具体日期。简短复盘只要包含具体事件、判断和改进动作即可正常评分；仅工作总结可以适当较低，不机械判近零。

参考区间：90—100分为成果突出、表达清楚且有较好复盘；80—89分为推进扎实、信息具体；70—79分为正常工作、主要信息基本清楚；60—69分为有记录但部分状态或思考不明；50—59分为内容少、多数难以判断；50分以下为大面积未填写、明显敷衍或严重不一致。没有自动保底分，也不因为缺附件压到低分。

## 隔离与复核

- 引擎：`server/report-quality-coaching.mjs`，规则 `weekly-quality-coaching-preview-2026-11-19-v1`、提示词 `weekly-quality-coaching-preview-prompt-2026-11-19-v4`。显式 `mode:'preview'` 才能调用，无数据库、网络或发布入口。
- 现行 `server/report-quality-scoring.mjs` 的规则、权重和历史解析完全保留。兼容历史评分的 `usableQuality` 明确拒绝带 preview 标识或候选版本的结果，防止其成为历史回退分。
- 四案例来自同周销售、采购、供应链、职能各一份，按岗位及模块完整性选择；旧分取真实保存值，不重新调用旧模型。新分使用原模型和未截断的四模块原文，使用同一候选提示词。
- 最终对比统一增加同模型的 AI 输出复核，版本 `weekly-quality-coaching-preview-review-2026-11-19-v1`。复核检查模型的原文理解、模块归属、时态和扣分理由，修正客观规则错误；不审计员工、不追求分数升降或岗位排名。初次及复核请求、原始响应、初次分析、最终分析均独立保留，复核不是人工确认。
- 如果独立检查发现可定位的原文归属、业务方向或评分规则错误，可用 `--review-feedback` 提供按案例 ID 索引的诊断字符串数组，再做一次明确诊断的纠错调用。诊断不指定目标分数；模型仍须依据同一原文与细则输出完整结果，程序不直接改分。纠错前分析、请求、响应和使用量均单独保留，失败不回填默认分。
- 比较工具 `scripts/compare-report-quality-coaching.mjs` 只接收显式输入文件和显式 provider 程序。通过 stdin/stdout 传输请求；不接入线上评分接口、缓存或数据库，也不写 AI 使用量。新输出目录必须不存在，已有比较不会被覆盖。
- 私人输入、原始模型响应、原文指纹、结果和 HTML 均存储在 Git 忽略的 `outputs/`，目录0700、文件0600，业务数据不入库提交。真实密钥不得写入请求、响应或仓库。
- 评分前后对四条生产周报做只读来源哈希核验。逐份人工检查分数、建议和异常判断；结构验证不能代替语义确认。

工具示例（provider 由运行者配置，只接收一个 chat-completions JSON 请求并输出一个响应）：

```sh
node scripts/compare-report-quality-coaching.mjs \
  --cases outputs/private-cases/cases.json \
  --out outputs/private-cases/new-comparison \
  --provider-program /absolute/path/to/node \
  --provider-arg /absolute/path/to/private-provider.mjs \
  --review-provider-program /absolute/path/to/node \
  --review-provider-arg /absolute/path/to/private-provider.mjs
```

输入需有四个岗位、原始四模块、保存的评分和模型；若附有原文及原评分 SHA，工具会逐项核对。输出中的 `previewOnly`、`humanConfirmationRequired` 和 `publicationMode` 明确标注试评，不构成上线或历史分覆盖。

专项检查：`npm run test:report-quality-coaching`。真实四案例比较还需人工复核；纯测试使用明确标注的虚构文字，不替代员工实际案例。
