# 全公司人员同步

2026-10-28 用户明确要求“公司全部人员都要纳入”，取代仅由首次SSO或历史周报发现员工的限制。本次只在本地实现和同步，不授权生产部署或仓库推送。

## 入口与范围

系统设置 → 员工管理 → 同步公司全部人员。

1. 使用应用身份读取通讯录授权范围、飞书根目录总人数与全部可见子部门。
2. 包含根部门直属人员，每个部门及用户列表均处理分页，再补充显式授权的独立人员。
3. 以准确 `user_id` 去重，多部门成员不重复入册，同名的不同账号继续分别显示。
4. 尚未登录人员也进入员工花名册，显示“已从飞书收录 · 尚未登录”；不伪造SSO登录记录。
5. 本次获取人数与飞书根目录总人数精确相等且分页无异常，才标记公司范围覆盖；缺少姓名或资料仍明确显示待补全。拿不到总数时仅在根目录全部授权且遍历成功时认可公司覆盖。

需要应用身份的 `contact:user.base:readonly` 与相应通讯录读取／user_id权限，并保证通讯录可见范围覆盖全部员工。用户身份权限不能代替后台应用身份权限。姓名暂时不可读时，仅按相同user_id使用已知姓名；未知姓名标为“待同步姓名”，不把ID伪装为姓名。

## 数据保护

- 保留本地停用状态，飞书同步和SSO均不自动恢复；飞书明确返回离职、冻结或未加入状态时，新账号不进入在职统计。
- 原有账号未被本次飞书返回时保留，单独提示数量供核实，不推断为离职，不删除或停用。
- 不调整老板或管理员角色，不自动指定评分人、不创建评分周期、不发送提醒或消息。全员进入花名册后，正常的人员范围、入职日期和手动配评流程继续适用。
- 已有在职日期和人工核实记录保留。新员工优先使用飞书入职日期；缺失则从首次发现当天开始，不倒推过去缺交。新发现的远端停用账号立即创建并闭合首次发现期间，跨月重启不会漂移日期。
- 并发SSO补齐的姓名、邮箱和部门，不被缺字段同步结果覆盖；并发停用不会被同步恢复。SSO补齐姓名时清除原缺名提示。
- 新增表 `employee_directory_profiles` 只记录来源、姓名缺失标记和同步时间。最近同步结果保存于 `app_settings.employee_directory_sync`，操作日志保留每次手动同步记录。没有删除或重建原表。

## 页面与验证

花名册展示本地总人数、在职、停用与未登录人数，支持姓名、部门、user_id搜索和人员状态筛选。列表内部滚动；页面刷新只读取最近结果，不会自动发起同步。

### 停用与恢复（2026-10-29）

- 老板或管理员进入「系统设置 → 员工管理」，在职人员右侧可「停用」，已停用人员右侧可「恢复」，均需确认操作。正式飞书登录与本机开发模式使用相同的人员管理权限校验。
- 恢复从北京时间当天开始新增在职区间（`manager_restore`），保留原有关闭区间。停用间隔不补计周报缺交；历史成绩、评分记录和已停用配评关系不自动改写。后续配评可在配评工作台重新配置。
- 同日停用再恢复会保留同日区间边界，按日期是否在任一区间内计算，不重复计数。重复恢复不创建多条开放区间；人员状态、区间、停用未完成配评和操作日志统一事务保存。
- 停用账号不登录、不参与新周报导入和 AI 分析、不进入新评分与提醒；飞书同步与 SSO 不自动取消人工停用。恢复账号重新进入后续业务范围。
- 在职日期详情优先显示最新开放区间，恢复日期与最初入职日期分开标记，多段历史只读展示。此功能在本地验证后仍需用户单次明确授权才可推送生产。

专项验证：`scripts/test-employee-status-api.mjs` 与 `scripts/test-company-roster-ui.mjs`。所有账号与上游请求使用隔离测试数据，测试不会恢复真实停用人员或发送消息。

隔离测试：`scripts/test-company-directory.mjs`、`scripts/test-company-roster-ui.mjs`；包括全员分页、根目录成员、显式授权、同名ID、未登录入册、停用保护、历史保留、幂等、资料缺失、范围不足、异常分页、并发SSO与跨月日期稳定。测试不读取真实飞书或发送消息，产物保留在 `outputs/tests/`。
